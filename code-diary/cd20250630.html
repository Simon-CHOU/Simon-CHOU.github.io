Java21 开发一个生产级别的Spring Boot 3.0 的后端服务项目会遇到哪些问题问题？

从session搜集问题。

项目启动报错 org.springframework.boot.docker.compose.core.ProcessExitException: ‘docker version –format {{.Client.Version}}’ failed with exit code 1. 原因：项目用了 spring docker compose 但是本地忘了启动 docker desktop

创建E-R图，但是光考虑符合范式，设计出来的schema 有问题 xNF范式，反范式，能不能完全搞清楚。最佳实践中的“反范式”能不能枚举出来。 冗余的字段（ audit_log 日志流水表可以多冗余点字段）。 每个表没有一个单独的id字段。 忘了一并创建 version, created_by, created_time, updated_by, updated_time （元字段应该有数据库层面的防篡改） id 字段到底用 bigserial 还是雪花，还是 UUID 外键之外，需不需要给增加 constrain 给业务字段

拆解用户故事，写好标题-估点-说明-AC1AC2AC3 拆解后端story card，要排除前端GUI的内容，也排除联调的内容。 写了Story之后，就要照着Story来了，story如果潦草不能信任，那么每一次开发都要回去看prd原文，极不讲究。 stroy 里要写清楚性能要求：索引，并发控制，事务隔离（级别）。 markdown mermaid ER图前后不要加 ~~ 符号。

拆Story 时，不要发挥出比prd文档还多的东西，控制范围。

创建ddl之后，靠flyway初始化，反复启动起不来。不要浪费时间重复启动应用（编译浪费时间），先把ddl单独在dbeaver中调通。 问题枚举： id 自增约束没设置（bigint primary key->bigserial primary key)。 dml insert 漏了id，违反非空校验。

分布式生成ID方案：uuid/自增/雪花方案。 一开始想一步到位 雪花。 但是1、雪花的原理不透彻。 2、通过pgsql自己创建雪花Id的的方法不知道（用函数还是插件） 3、有额外依赖，貌似有时间戳的影响，分布式服务器节点id的影响。4、不知道选用哪个雪花算法库。

调试过程中，因为高级语法（on conflict ）似乎不兼容。所以还需要查询db版本： SELECT version(); vn -X flyway:migrate mvn flyway:migrate -X DML 初始化语句调试，出现了table does not exists 的问题。 violates foreign key constarint violates foreign key constraint “fk_contracts_drug” , 插入A表的数据时关联的B表记录尚不存在。 violates check constraint “chk_drugs_expiry_date” ，数据库层面的业务校验（一般来说可以删掉）

dml 关联表中，使用了key1-key 联合主键，没有独立id。 问题触及了数据库设计中一个核心的权衡： 使用代理主键（Surrogate Key）还是自然/组合主键（Natural/Composite Key） 。 单独的id 有利于写更新sql。

最终还是放弃了雪花，使用了BIGSERIAL

postgresql 枚举类型的用法。DROP TYPE IF EXISTS … CASCADE;

dml insert 报错： 1、已存在的列没有值。 2、插入的值列、表还不存在。 修改 dml/ddl flyway 启动执行成功后，记得补充文档 字段、字段类型，约束，id生成方式 等。。 一些花边： 新增和完善了设计说明 ：补充了关于 BIGSERIAL 、 JSONB 数据类型、公共字段、自动化机制（如 updated_time 触发器）以及索引策略的详细说明。

有了er图和DDl，就可以拆接口，restfulpai 考虑api的可测性，比较玄：

### 可测试性设计（TDD/Agile友好）

  • 契约测试 ：支持OpenAPI规范

  • 测试环境 ：提供数据重置和Mock支持

  • 健康检查 ： /health 和 /metrics 端点

疑点：_link 到底要不要。HATEOAS

### 非功能性需求 - 安全性 ：JWT认证、RBAC授权、HTTPS强制 - 性能 ：响应时间要求、并发支持、缓存策略 - 监控 ：结构化日志、指标暴露、请求追踪 - 版本管理 ：向后兼容策略、废弃通知机制
